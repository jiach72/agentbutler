## 三、安全审计（专项 agent 完成，K-1 已人工复核属实）

> 威胁模型：本地单用户、默认仅回环发布。以下按该模型评级。

### 【High】K-1 知识库 upload-vault 路径穿越：任意文件写 + 任意文件删 + 任意读

`apps/web/src/routes/knowledge.ts:1111-1120`（写）、`:761-768`（删）、`:1426` 附近（读）：

```ts
const cleanRel = item.path.replace(/^[/\\]+/, "").replace(/\\/g, "/");
...
const fullDest = join(targetBase, cleanRel);
...
writeFileSync(fullDest, Buffer.from(item.content, "base64"));
```

- `cleanRel` 只剥开头部的 `/` `\`，**未处理 `..` 段、无 `inside()` 边界断言、无符号链接校验**（对比同仓库 `apps/watch/src/markdown-files.ts:47-50,104-107` 的正确实现，水位落差明显）。`item.path = "..\\..\\x"` 清洗后即 `../../x`，逃出 `documentsDir`；含 `..` 的路径随后写入 manifest，DELETE / preview 路由再 `join(documentsDir, doc.path)` 直读直删。
- **可利用链**：面板有权者（或 K-2 DNS rebinding 组合）可覆盖 web 容器内 `/app/ui/dist` JS 资源（node 属主，web Dockerfile:53-69）形成**持久化 XSS**，或篡改 `butler-data` 共享卷中的 SQLite / `github-token.json`。
- **修复**：复用 markdown-files 的 `inside()` + realpath 模式；manifest 落库前拒绝含 `..` 的 path；写/删/读三处统一做边界断言。
- ✅ 本报告作者已亲自读源码复核，确认属实。

### 【Medium】K-2 无 Host 头白名单 → DNS Rebinding 可绕过回环便利通道与 CSRF 防线

`apps/web/src/server.ts:263-271`、`apps/web/src/http-auth.ts:49-56`。回环判定用 TCP 对端地址（正确，F-03 审计修复），但 Origin 同源比较依赖 Host 头，而 Host 未校验：rebinding 后 `Origin` 与 `Host` 天然一致 → 放行且免口令。与 K-1 组合升级为容器内任意文件写。**修复**：加 Host 白名单（loopback + `BUTLER_WEB_PUBLISH_HOST` + 显式配置域），其余 403。

### 【Medium】K-3 watch 把整个 RFC1918 内网当"回环"（默认开启）

`apps/watch/src/http-common.ts:958-964`：`BUTLER_CREDENTIAL_WRITES_ALLOWED` 默认 true（compose 缺省），`172./10./192.168.` 源 IP 全部放行写请求（凭据保存、killswitch 等）。注释宣称"仅允许回环"与实现不符；compose 内任意被攻陷容器（如第三方镜像 AnythingLLM）可横向驱动 watch。**修复**：服务间调用统一走 deploy.sh 已自动生成的 `BUTLER_INTERNAL_TOKEN`，把 RFC1918 放行改为显式 opt-in。

### 【Medium】K-4 gateway 内部口令只护住 `/api/messages/*` 前缀

`apps/gateway/src/server.ts:499-503`。无访问口令部署下，`POST/DELETE /api/bots`（写 `~/.hermes/profiles/`）、`POST /api/alerts`（可无限投递到 Telegram）仅靠"无 Origin 即放行"的 CSRF 兜底（`:545-552`）。缓解：7532 仅 compose 内 expose，deploy.sh 默认生成内部口令。**修复**：内部口令钩子覆盖所有状态变更方法（白名单豁免 healthz / telegram webhook）。

### 【Medium】K-5 watch 的 Origin 白名单接受可伪造的 `butler-web` 主机名

`apps/watch/src/http-common.ts:902-914`。`Origin` 头由攻击者页面控制，与 K-3 组合时可穿透两层防线。**修复**：从 loopback 判定中移除 `butler-web`。

### 验证过的安全亮点（值得保持）

1. **凭据加密**：AES-256-GCM + 每次独立随机 12 字节 nonce + fail-closed；主密钥 32 字节强校验，`deploy.sh:43-73` 生成后 `chmod 600 .env` 且拒绝 shell/env 双源不一致（防误轮换）。
2. **updater 注入面**：全 `execFile` 数组传参、`SAFE_TARGET` 正则防 git 旗标注入、服务启动白名单、无口令 fail-closed——全仓库注入面控制最好的模块。
3. **Python 桥边界**：bind 强制 loopback（非 loopback 直接抛错，与 AGENTS.md 描述的崩溃循环一致）；token 文件拒符号链接、0600、属主校验；YAML 全 safe_load/safe_dump + 原子替换 + 自动备份。
4. **口令卫生**：token 不进 URL（WS 用 60s 一次性 ticket）、比较全部 timing-safe（含长度不等时 `timingSafeEqual(b,b)` 等耗时补齐）、Telegram 错误摘录统一脱敏、bridge URL 强制 http+loopback+无凭据。
5. AGENTS.md 第 5 节安全红线逐条在代码/compose 中验证兑现，**未发现"文档声称但代码未实现"**。

## 四、后端正确性与架构

- **SQLITE_BUSY**：四处 DB 打开点（gateway queue/store、web ollama store、core store）统一 `PRAGMA busy_timeout=5000`，且有跨进程共享说明（`packages/core/src/store.ts:550-551`）。
- **SQL 注入面干净**：全仓 grep 无字符串拼接 SQL；模板字面量均为多行书写 + `?` 占位符。

- **契约共享**：`packages/contract`（zod）被前后端真实引用，非复制粘贴类型。
